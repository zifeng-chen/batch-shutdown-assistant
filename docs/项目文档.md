## 1. 项目概述

### 1.1 要解决的问题

联想门店的样机每天要经历一套固定动作：出样（Sysprep 回到 OOBE）、关机、重启、展示通知、统计硬件、更新软件。这些动作单台手动做没问题，几十上百台就是纯粹的体力消耗，而且容易漏、容易不一致。

Windows 11 家庭版还额外限制了做法——没有组策略、没有域，传统批量管理手段用不上。系统就是针对这个约束设计的。

### 1.2 设计取向

| 取向 | 具体体现 |
| --- | --- |
| 家庭版优先 | 不依赖域、组策略、WinRM；只用服务 + HTTP/WS |
| 单文件部署 | Agent 是一个 exe，无运行时、无依赖 |
| 弱网可恢复 | 两条通道独立，任一断开都能自愈 |
| 现场可诊断 | 日志落盘、安装日志写 U 盘、上报空 IP 而非假 IP |
| 管理端单一入口 | 单端口同时提供 REST、WebSocket 与静态页面 |

### 1.3 核心能力

| 能力 | 说明 |
| --- | --- |
| Sysprep 出样 | 执行系统准备工具并关机/重启，不消耗 Rearm 次数 |
| 远程关机 / 重启 | 单台或批量，逐台回报 |
| 弹窗通知 | 桌面投放提示窗口 |
| 硬件信息采集 | CPU、内存、磁盘、系统版本、序列号、MAC、厂商型号 |
| 文件分发 | 推送文件到指定目录 |
| 密码修复 | 清空当前账户密码，修复 Sysprep 后登录失败 |
| 推送升级 | 管理端一键推送新 Agent |
| 自动注册 | 安装即上线；重装自动接管原记录 |
| 远程卸载 | 删除设备时自动清理服务与目录 |
| 离线自毁 | 可选，默认关闭 |

### 2.1 组成

```
┌──────────────────────────────────────────────┐
│ 管理端                                        │
│ ┌────────────────┐  ┌──────────────────────┐ │
│ │ FastAPI        │  │ Vue3 SPA (static/)   │ │
│ │ REST + WS      │  │ Element Plus         │ │
│ └───────┬────────┘  └──────────────────────┘ │
│         │                                    │
│ ┌───────┴────────┐  ┌──────────────────────┐ │
│ │ SQLAlchemy     │  │ 后台任务             │ │
│ │ async          │  │ 离线巡检 / 维护      │ │
│ └───────┬────────┘  └──────────────────────┘ │
│         │                                    │
│ ┌───────┴────────┐                           │
│ │ SQLite         │                           │
│ └────────────────┘                           │
└──────────────┬───────────────────────────────┘
               │
     ① 心跳 HTTP POST（15s）
     ② 长连接 WebSocket
               │
┌──────────────┴───────────────────────────────┐
│ 被管理端：Go 单文件 Agent（Windows 服务）      │
│ Windows 11 家庭版 ×N                          │
└──────────────────────────────────────────────┘
```

### 2.2 技术选型

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 管理端框架 | FastAPI | 异步、自带 OpenAPI、WebSocket 支持好 |
| ORM | SQLAlchemy 2.0 async | 类型安全、异步原生 |
| 数据库 | SQLite + WAL | 单机规模足够，零运维；WAL 支持并发读写 |
| 前端 | Vue 3 + Element Plus | 组件齐、表格/表单场景成熟 |
| 状态 | Pinia | 轻量 |
| 图表 | ECharts | 统计页需要 |
| Agent | Go（`CGO_ENABLED=0`） | 单文件、无运行时、Windows 服务 API 支持好 |
| Agent 持久化 | JSON 文件 | 配置量极小，无需数据库 |

### 2.3 为什么是两条通道

这是整个架构最关键的一个决定。

**只用 WebSocket 不行**：长连接断了就完全失联，管理端不知道设备是死是活。
**只用 HTTP 轮询不行**：指令下发延迟取决于轮询间隔，实时性差，且服务端要保存待发指令队列。

所以拆开：

| 通道 | 承担 | 特点 |
| --- | --- | --- |
| 心跳 HTTP | 存活证明、状态上报、配置下发 | 短连接，失败可重试，无状态 |
| 长连接 WS | 指令接收、结果回传 | 长驻，双向，实时 |

代价是：**两条通道可能一个通一个不通**。"设备在线但指令无响应"这个历史高频问题就源于此。文档在 [排障手册 2 节](排障手册.md) 专门处理了这种情况。

### 2.4 单端口

管理端的 REST API、WebSocket、前端静态资源全部跑在同一个端口（默认 8900）。

好处：部署简单、防火墙只开一个口、反向代理配置简单。
代价：WebSocket 必须显式配 `Upgrade` 头，否则被降级。

历史上曾用 8080（Python 版管理端）与 8900（另一套运营系统）双端口并存，后统一收敛到单端口。

## 4. 核心流程

### 4.1 设备首次注册

```
Agent 启动
   ↓
读 config.json（可能无 device_id）
   ↓
POST /api/agents/heartbeat
   带 X-Enroll-Secret
   ↓
管理端：无匹配记录 → 校验注册密钥
   ├ 失败 → 401 Enrollment secret required
   └ 成功 → 新建 Device 记录 → 返回 { device_id, status:"created" }
   ↓
Agent：归一化 device_id → 写 config.json + 内存 liveCfg
   ↓
建立长连接 /ws/agents/{device_id}
```

注册过程串行化：Agent 启动瞬间可能并发多个心跳，不加锁会"都查不到记录 → 都新建"，产生重复设备。

### 4.2 正常心跳

```
每 15 秒
   ↓
POST /api/agents/heartbeat（带 device_id + token）
   ↓
管理端：device_id 精确匹配 → 令牌一致
   ├ hostname_locked 为 false → 更新 hostname
   ├ 刷新 ip（payload.ip 非空时）
   ├ 刷新 rearm_count / agent_version / sysinfo
   ├ last_heartbeat = now
   └ status = online
   ↓
返回 { device_id, status:"updated", offline_selfdestruct_hours }
```

`ip` 为空时**不覆盖**已有值——设备临时断网不该把 IP 清掉。

### 4.3 重装接管

```
设备重装 → 新 token，可能沿用原 IP
   ↓
心跳：按 device_id 匹配失败 → 按 IP 匹配到旧记录
   ↓
令牌不一致
   ├ 记录已软删除 或 X-Enroll-Secret 正确
   │     → 接管：更新身份、轮换 token、清 deleted_at
   │     → 返回 status:"re-enrolled"
   ├ 已软删除且无有效密钥 → status:"deleted"
   └ 其余 → 401 Invalid agent token
```

这条路径是"设备被删了又重装"能自动回来的关键，也让别人无法用同一 IP 抢占已有设备。

### 4.4 指令下发

```
管理端：POST /api/tasks  { task_type, device_ids, params }
   ↓
创建 Task + 每个设备一条 TaskResult
   ↓
action 统一转小写
   ↓
通过长连接推送 { id, action, params }
   ↓
Agent：handleCommand 按小写匹配
   ↓
执行 → 写回 { id, status, output }
   ↓
管理端更新 TaskResult，前端通过 /ws/tasks/{task_id} 看进度
```

### 4.5 覆盖安装

```
用户管理员运行 reinstall.bat
   ↓
检查管理员权限
   ↓
检查包内文件完整性（LanAgent.exe / deploy.conf）
   ↓
停止并删除旧服务注册
   ↓
按路径匹配结束残留进程（不按映像名全局杀）
   ↓
删除旧 exe / config.json / deploy.conf
   ↓
复制新文件
   ↓
重新创建并启动服务
   ↓
保留 logs 与 data
```

Agent 启动时还有一层迁移：若检测到旧路径 `C:\Windows\LanAgent`，先迁移其中的 `logs`、`data`（目标已存在则保留不动），再删除旧目录。

### 4.6 设备删除

```
管理端删除设备
   ↓
写 deleted_at（软删除）
   ↓
若设备在线 → 推送 uninstall 指令
   ↓
Agent 停止并删除服务、清理安装目录
```

软删除而非物理删除，是为了让重装的设备能被识别并恢复。需要彻底清理时用批量删除。

## 5. 数据模型

### 5.1 Device

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | String(36) | 主键，UUID |
| `hostname` | String(255) | 主机名 |
| `hostname_locked` | Bool | 锁定后心跳不覆盖主机名 |
| `ip` | String(45) | 局域网 IP |
| `os_info` | String(255) | 系统描述 |
| `status` | Enum | `online` / `offline` / `generalized` / `recovering` |
| `group_name` | String(100) | 分组 |
| `rearm_count` | Integer | Sysprep 剩余次数，`-1` 取不到 |
| `agent_version` | String(20) | Agent 版本 |
| `cpu_model` | String(255) | CPU 型号 |
| `cpu_cores` | Integer | 核心数 |
| `memory_total_mb` | Integer | 内存 |
| `disk_total_gb` | Integer | 磁盘总量 |
| `disk_free_gb` | Integer | 磁盘剩余 |
| `os_version` | String(255) | 系统版本号 |
| `serial_number` | String(255) | 序列号 |
| `mac_address` | String(255) | MAC |
| `manufacturer` | String(255) | 厂商 |
| `model` | String(255) | 型号 |
| `sysinfo_updated_at` | DateTime | 硬件信息采集时间 |
| `token` | String(255) | Agent 令牌，索引 |
| `last_heartbeat` | DateTime | 最后心跳 |
| `created_at` / `updated_at` | DateTime | 时间戳 |
| `deleted_at` | DateTime | 软删除标记 |

### 5.2 Task / TaskResult

| 表 | 关键字段 |
| --- | --- |
| `tasks` | `id`、`task_type`（枚举）、`status`（pending/running/completed/failed/cancelled）、`params`(Text)、时间戳 |
| `task_results` | `id`、`task_id`(FK)、`device_id`(FK)、`status`、`output` |

一个任务对多台设备 → 多条 TaskResult，逐台记录成功或失败。

`output` 截断 10 万字符，防止单条结果撑爆数据库。

### 5.3 TaskType 枚举

```
sysprep  sysprep_reboot  shutdown  reboot  status
upgrade  file_push       hostmsg   sysinfo  reset_pwd
```

与 Agent 侧 `handler.go` 的 case 分支**一一对应，且全部小写**。

### 5.4 AuditLog

记录登录失败与锁定、设备增删、指令下发、升级推送等关键操作。保留 180 天 / 20 万条上限，由每日维护任务清理。

### 5.5 时间约定

统一使用北京时间 naive datetime（`now_bjt()`），与数据库 `DateTime` 列匹配。

需要注意：离线巡检用原生 SQL 更新状态时，原生 SQL 不走 SQLAlchemy 的 Enum 类型处理器，必须用枚举成员名（大写 `ONLINE`/`OFFLINE`）匹配——用小写值会更新不到任何行，表现为"离线检测完全失效"。

## 6. 后台任务

| 任务 | 周期 | 作用 |
| --- | --- | --- |
| 离线巡检 | 10 秒 | `last_heartbeat` 超过 15 秒的在线设备标记离线 |
| 维护循环 | 24 小时 | 清理超期审计与过期上传文件 |

离线判定阈值 `HEARTBEAT_TIMEOUT_SECONDS = 15`，与 Agent 心跳间隔一致。心跳间隔等于超时阈值意味着**一次丢包就可能被判离线**——这是有意的取舍：门店网络丢包率低，宁可短暂误判也不要长时间显示假在线。

### 6.1 离线自毁

`OFFLINE_SELF_DESTRUCT_HOURS`，**默认 0 = 关闭**。

开启后 Agent 连续无法连接管理端超过阈值会自行卸载。默认关闭是因为：管理端宕机、网络中断、机房搬迁都会让全部门店设备同时进入倒计时，一旦误触发就是整批设备消失，且无法远程恢复。

阈值随每次心跳下发，管理端可随时调整。

### 7.3 排序

后端 `device_routes.py` 的 `ip_sort_key`：

```python
def ip_sort_key(device):
    """IP 数值排序键；非法或缺失 IP 排到末尾"""
    try:
        return (0, int(ipaddress.IPv4Address(device.ip)), device.hostname or "")
    except (ipaddress.AddressValueError, ValueError, TypeError):
        return (1, 0, device.hostname or "")
```

按**数值**而非字符串排序，跨网段正确：`192.168.2.9` 在 `192.168.2.10` 之前。在 Python 层排序而不是 SQL `ORDER BY`，是为了不依赖数据库方言的 IP 处理能力。

### 7.4 版本号兜底

升级对话框里的版本号优先取服务端返回；服务端不可达时用 `Devices.vue` 里写死的兜底值。这个值由 `build.sh` 自动同步，不要手改。

## 8. 构建与发版

### 8.1 版本号唯一来源

`server/config.py` 的 `APP_VERSION`。

`build.sh` 会同步到三处：

1. `web/package.json` 的 `version`
2. `agent/heartbeat.go` 的 `buildVersion` 默认值
3. `web/src/views/Devices.vue` 的版本兜底值

Agent 实际版本由编译期 `-ldflags "-X main.buildVersion=…"` 注入，`buildVersion` 的代码默认值只是没有注入时的兜底。

**不要在别处手改版本号**，否则会出现"管理端显示 A 版本、Agent 自报 B 版本、exe 里是 C 版本"的三方不一致——这类问题排查成本很高。

### 8.2 构建

```bash
./build.sh                  # 全量
./build.sh --agent-only     # 只编译 Agent
./build.sh --web-only       # 只构建前端
./build.sh --skip-tests     # 跳过测试
./build.sh --version 1.7.7  # 指定版本并回写 config.py
```

只编译 Agent 时的等价命令：

```bash
cd agent
GOOS=windows GOARCH=amd64 CGO_ENABLED=0 \
  go build -ldflags "-s -w -X main.buildVersion=1.7.6" -o LanAgent.exe .
```

`CGO_ENABLED=0` 是必须的——否则产物依赖外部 C 运行库，无法单文件分发。

### 8.3 发版流程

1. 改 `server/config.py` 的 `APP_VERSION`
2. 更新 [更新日志](更新日志.md) 与相关文档
3. `./build.sh`，确认测试全通过
4. 提交、推送、打 tag `vX.Y.Z`
5. 管理端上传新 `LanAgent.exe`
6. 设备页推送升级，确认版本号已变

### 8.4 只改客户端时的处理

如果改动只在 Agent（不涉及服务端接口与数据库），**不需要发新版本号**，直接替换发行目录里的 `LanAgent.exe` 即可——安装包由管理端现场生成，exe 换了之后新生成的安装包自然带新版本。

判断标准：改的是 `agent/*.go` 还是 `server/`。前者不发版，后者要发。

## 10. 已知限制

| 项 | 说明 |
| --- | --- |
| 传输明文 | 默认 HTTP，内网中间人可篡改 |
| token 在 query | 长连接 token 出现在 URL，会被代理与访问日志记录 |
| 无签名校验 | 上传 exe 只校验 PE 头 |
| JWT 不可撤销 | 靠 30 天过期 |
| 本地配置明文 | `config.json` 中 token 未加密 |
| 单机数据库 | SQLite 不适合多写节点，规模上限受单机限制 |
| 家庭版限定行为 | Sysprep 在家庭版的部分行为与专业版存在差异，系统在这条基线上验证 |

详见 [安全说明](安全说明.md)。

## 11. 版本演进要点

理解几个关键转折点，能避免在新环境里重复踩坑。

### 11.1 安装路径

```
C:\LanAgent              （最早）
   ↓
C:\Windows\LanAgent      （1.4.8 起，出现了目录权限问题）
   ↓
C:\Program Files\LanAgent （1.5.0 起，当前）
```

中间那段放在 `C:\Windows` 下，实际使用中出现了日志目录创建失败、采集不到信息等症状，最终改回 `C:\Program Files`。迁移逻辑现在双向兼容，两个旧路径都会被清理。

### 11.2 端口

```
8080（Python 管理端）+ 8900（运营系统）
   ↓
8900 单端口
```

收敛过程中出现的典型问题：`app.locals.sampleDevicesDb is not a function`——合并装配时漏挂依赖。

### 11.3 指令名大小写

早期下发大写 `SHUTDOWN`，Agent 侧 `switch` 按小写匹配，全部命中 `default` 分支，回报 `unknown action`。现在下发时统一转小写。

### 11.4 device_id 解析

> 这是整个项目里最值得记住的一个 bug。

服务端返回 `device_id` 是数字（数据库自增主键），早期 Agent 用 `string` 接收：

```go
var result struct {
    DeviceID string `json:"device_id"`
}
if err := json.NewDecoder(resp.Body).Decode(&result); err == nil {
    // 这里永远不执行
}
```

`json.Unmarshal` 遇到类型不匹配返回错误，而 `err == nil` 把它吞掉了。结果是：**心跳 HTTP 200、服务端日志一切正常、客户端 device_id 永远为空、长连接永远等不到值、指令永远收不到。**

日志当时是充分的，缺的是"不报错但拿到空值"这个失败模式的显式检查。修复分两层：

1. 用 `interface{}` 接收再归一化（`normalizeDeviceID`）；
2. 解析失败必须打日志，不能静默。

同时把 `offline_selfdestruct_hours` 改成 `*int`，区分"字段缺席"和"值为 0"。

### 11.5 日志策略

早期日志无限追加，现场回传的日志里绝大部分是历史噪声。现在只保留 10 分钟，且与管理端断开后停止写入、只记一条断开时间。

实现时踩过一个死锁：持锁调用 `log.Output` 会重新进入 `logWrite`。必须先解锁再写。
